How outbound mail works

  • Relay host — pick a real provider (Postmark, Mailgun, SendGrid, Brevo, AWS SES, Gmail SMTP) or point at a local postfix configured to relay outbound. Sending directly from a VPS to public mailboxes almost always lands in spam.
  • SPF — the recipient's mail server checks whether your relay's IP is on the From-address domain's permitted-sender list. Set this up with a DNS TXT record on your domain; Hyperion shows per-hosting SPF analysis on each hosting's detail page.
  • Sender address — must use a domain you control whose SPF includes your relay. Detection derives a sensible default from /etc/mailname.
  • Per-node — each worker has its own [email] section in its own agent.toml. Pick a node in the From dropdown above to verify that node's outbound path.
  • Every send is logged at Emails with the full SMTP response, so you can tell "queued" (250) from "rejected by relay" (550) without leaving the panel.

{# ───── Automatic updates. Off by default and deliberately so. ───── #}

Automatic updates

When on, this node checks hourly for a new Hyperion release and installs it in safe mode: the running binaries are snapshotted first, and restored automatically if the node does not come back healthy. Automatic and irreversible is a combination worth avoiding — you are asleep exactly when this fires.

System packages are not touched: an unattended apt dist-upgrade has a far bigger blast radius than a Hyperion update, and is not what this promises. Run that from Nodes when you are watching.

Note that a rollback restores binaries, not data. Migrations in this project are additive, so an older binary starts against a newer schema — which is the case this is built to survive.

Failures inside the window before a ban

Website login counts POSTs to wp-login.php and xmlrpc.php in one site's access log, so the ban is recorded against that site and shows up in its care report. How long a ban lasts

An address that was already banned within the look-back window gets the longer repeat-offender ban instead of the first-offence one. Set the look-back to 0 to never escalate. A ban shorter than a minute is refused: the ban list reads a zero duration as never expires.

Only public, routable addresses are ever banned automatically. Private, loopback, CGNAT and link-local addresses are skipped, because a node-wide firewall drop on those is an outage — webmail talking to dovecot, the master↔node link, a NAT gateway in front of the whole office. {# ─── Cluster channel hardening ─────────────────────────────── Three rungs, and the order is load-bearing. Step 0 is not a toggle: it lives in each node's own agent.toml because it is the node that decides whether to trust the master's cert, and it comes first because it is the leg that carries the node's plaintext secret. Steps 1 and 2 are master→worker: step 1 keeps an on-path attacker out of the channel, step 2 keeps the master from believing what comes back if the channel is defeated anyway. Turning on step 2 alone still leaves every secret in a reply (reset passwords, enrollment tokens) readable on the wire, so the numbering is UI, not decoration. #}
Cluster channel hardening

Every command the master sends already carries an Ed25519 request signature, so a worker never acts on a forged instruction. The steps below protect the rest of the exchange — who can read the channel, and whether the master can trust the answer. Work through them in order, and only after Nodes shows the matching chip on every node.

Step 0 · Each node verifies this master's certificate. Not a switch here — it is set per node, in /etc/hyperion/agent.toml under [enrollment], because the node is the side that decides whom to trust. It comes first because it is the leg that carries each node's own secret, in the clear, on every heartbeat. The node installer measures it: if this master already serves a CA-issued certificate it writes verify_tls = true; if the certificate is self-signed it writes verify_tls = false and says so. With verify_tls absent the agent verifies whenever this master's URL is https:// with a DNS hostname. A failed check is never retried unverified — the node stops heartbeating and prints the fix, so a node that has gone stale on Nodes right after you changed the master's certificate is telling you something. Check with journalctl -u hyperion-agent -g 'TLS policy' on the node.

When on, the master refuses any RPC to a worker whose TLS certificate doesn't match the SPKI pin that worker reported on its heartbeat. This shuts a man-in-the-middle out of the channel entirely, which is why it comes first. A pin is recorded once and never silently replaced: a worker that reports a different pin later is refused and logged, so nothing on the wire can re-aim the pin the master enforces against. Turn this on only after every node on Nodes shows 🔒 TLS pin on file and you have seen no warn-only pin-mismatch warnings in the logs. While this is on, a worker with no pin on file is refused too — with nothing to check the certificate against there is no protection to give it, and suppressing the pin report is exactly how an attacker would arrange that. So a worker that is still mid-upgrade, or whose agent has been restarted within the last heartbeat, will be cut off until its 🔒 chip appears. A stale pin behaves the same way: use Clear pinned crypto on that node's card after a key change you expected. Applies within about 30 s; no restart needed.

A node that has published a response-signing key signs every reply, and the master verifies it. A mis-signed reply is discarded whether or not this is on. Trash / soft-delete

Backup-archive retention is separate — it lives with its backups on the Backups tab. When on, deleting a hosting moves it to Trash: nginx serves 503, FPM stops, and the database and OS users are locked, but the files, database, certificates, and user are preserved. After the retention window, the scheduler runs the permanent-delete pipeline automatically. When off (the default), deletes are permanent immediately, as before.

{# Tell post_config to land us back on /settings#retention instead of the section→tab default (which would send us to #cluster). #}

The scheduler permanently deletes any trashed hosting older than this. Before the timer expires, you can still Restore a hosting or Delete it permanently from Trash.

Audit log retention

The audit log records every state-changing operation as a tamper-evident BLAKE3 hash chain. Without retention it grows indefinitely — on a busy cluster, tens of MB per month. Set a window in days below to purge older entries automatically; the chain re-anchors at the oldest surviving row, so verify_chain still works on what's left. 0 (the default) keeps everything forever.

Typical values: 90 for compliance-light setups, 365 for tighter rules, or 0 if you export /audit?export=csv off-cluster and want everything kept locally. Purges run on the normal scheduler tick (about every 60 s); no extra cron job is needed.
