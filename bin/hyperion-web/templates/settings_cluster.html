What each step protects

Every command carries an Ed25519 request signature, so a worker never acts on a forged instruction. The order of the steps matters: signed replies on an unpinned channel can still be read on the wire. Nodes show what they have on file on Nodes (open a node → Connection). Both switches apply within about 30 s.

0 · The node verifies the master. It comes first because this leg carries each node's own secret, in the clear, on every heartbeat. The node installer measures it: a master serving a CA-issued certificate gets verify_tls = true; a self-signed one gets false, and the installer says so. With the key absent, the agent verifies whenever the master's URL is https:// with a DNS hostname. A failed check is never retried unverified — the node stops heartbeating and prints the fix, so a node that goes stale right after you change the master's certificate is telling you something. Check with journalctl -u hyperion-agent -g 'TLS policy' on the node.

1 · Pinning. The master refuses any call to a worker whose TLS certificate does not match the pin that worker reported on its heartbeat, which shuts a man-in-the-middle out of the channel. A pin is recorded once and never silently replaced: a worker reporting a different one later is refused and logged. Turn this on only when every node has a pin on file and the master's hyperion-web journal (journalctl -u hyperion-web -g 'SPKI pin') shows no warn-only pin-mismatch warnings. While it is on, a worker with no pin on file is refused too — suppressing the pin report is exactly how an attacker would get around it — so a worker mid-upgrade, or whose agent restarted within the last heartbeat, is cut off until its pin is on file again. A stale pin behaves the same way: after a key change you expected, use Clear pinned crypto on that node.

2 · Signed replies. A node that has published a response-signing key signs every reply. A mis-signed reply is discarded whether or not this is on; the switch adds refusing an unsigned reply from a node known to sign, which is what stripping the signature on the wire looks like. Turn it on only after step 1, once every node has a key on file — that, not the agent version, is the readiness signal. While it is on, a node with no key on file is refused too: an unverifiable node must not end up more trusted than one that merely dropped its signature.

How the sync works
  • A pass runs every five minutes, and a few seconds after any save that changes a synced setting. Only nodes that are behind get the settings.
  • The S3 targets travel too, so a worker's scheduled backups reach them.
  • A synced node's own settings page shows these values read-only: an edit there would be undone by the next pass.
  • A node on an agent from before the sync keeps its own settings until it is updated from Nodes; until then it still gets the ones its sites run by at the moment you save.
