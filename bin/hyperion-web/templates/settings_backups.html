What is kept

{{ protection.word }}

Archives bring a site back after a server is lost; snapshots undo a bad update.

{% if snapshots_only %}

Archives and snapshots

Backup archives are a tar of the site plus a database dump, made on each site's schedule and copied off-site. They answer “the server is gone”, and they are what a care package sells to a customer.

Snapshots are taken before Hyperion applies a site's automatic updates, and by hand from a site's Backups tab. Shared content is stored once, so thirty cost little more than one, and they can show what an update changed. They answer “last night's update broke the site”. They never leave the node.

Switching one off stops new copies; it never deletes what is already kept. Backups taken internally to undo a move, a copy or a staging push run in every mode — that is how those features roll themselves back.

How the FTP / SFTP copy works
  • Backups land on local disk first, under /var/lib/hyperion/backups/local, and are pushed here as soon as each one finishes.
  • Test connects, logs in and lists the base path, using the target as saved{% if chrome.has_nodes %}, from the master{% endif %}. It runs on its own after each save.
  • Hyperion never prunes or deletes anything on this server: clean up old copies there.
  • Plain FTP sends the password and every backup unencrypted. Prefer SFTP or FTPS.

S3 target

Add any S3-compatible bucket — AWS, Wasabi, Backblaze B2, MinIO. With an encryption key, copies are encrypted before they leave the node.

How S3 copies work
  • After each backup the node uploads the archive, the database dump and the manifest. With an age key each file is encrypted on the node and streamed (age → aws), so it needs no extra local disk.
  • Only the age public key is stored. Keep the private key somewhere safe, off the servers: it is the only way to read these copies.
  • After each upload the bucket is pruned to the newest copies per site set here; 0 keeps everything.
  • Every node needs the AWS CLI (apt install awscli), and age for encryption.
  • The secret key is kept in a 0600 file under /etc/hyperion/secrets/{% if chrome.has_nodes %} and handed to the other nodes by the settings sync{% endif %}. When editing, leave it blank to keep the stored one.
  • Test asks the bucket's address for an answer: it proves the endpoint and bucket name, not the keys.

Local copies

{{ local.word }}

Every backup lands on local disk first. Once its off-site copy is confirmed, the local one can be deleted to save disk.

When a local copy is deleted
  • After each backup of a site, its local archives and database dumps — this backup's and any older one already off-site, except the newest kept here — are deleted only once each off-site copy has been re-checked and confirmed present, never on a mere “upload finished”.
  • A copy that cannot be confirmed is kept, and the site's Backups tab says why. A node with no off-site destination never deletes anything.
  • A restore then comes from the off-site copy, through the Off-site copies card on the site's Backups tab.
  • Off by default: a local copy means a faster restore and a second copy, at the cost of disk.
  • Turning it on frees a site's existing copies after its next archive backup, on whichever node owns it. To free them now, use Copy off-site & delete local; for one site, Off-site & drop on its Backups tab.
    • {% if chrome.has_nodes %}
  • A node on an older agent has no keep count: with deleting on, it keeps no local copy at all. So it is not given deleting with a count above 0 — it keeps its earlier setting until it is upgraded.
    • {% endif %}
{% endif %}

Archive retention

{{ retention.word }}

Old archives are deleted after each new backup, but every site keeps its newest few however old they are.

How archive retention works
  • When a backup of a site completes, its archives older than the set age are deleted from the node — but its newest successful ones are always kept, so a site nobody has touched for months still has its last few backups.
  • A site's profile or care plan can set a longer history for that site.
  • Snapshots follow this rule too until Snapshot retention has been saved once.
  • Off-site copies have their own rule: an S3 target keeps the newest copies set on it, and the FTP / SFTP server is never pruned. Deleted sites wait in Trash.

How snapshot retention works

  • Single snapshots can be deleted by hand on each site's Backups tab.

Trash

{{ trash.word }}

{% if config.cluster.trash_enabled %}A deleted site waits in Trash, offline but intact, before it is removed for good.{% else %}Deleting a site removes it for good, straight away. With Trash on, it waits in Trash first.{% endif %}

What Trash keeps
  • A trashed site is offline: nginx answers 503, PHP-FPM stops, and its database and system users are locked. Its files, database, certificates and user are kept.
  • Until the time is up you can restore it, or delete it for good, from Trash. After that the scheduler runs the permanent delete on its own.
  • Off (the default) means a delete is permanent at once.
    • {% if chrome.has_nodes %}
  • A delete runs on the node that owns the site, and reads that node's copy of this setting.
    • {% endif %}

Maintenance

Copy existing backups off-site

Sends the backups that never reached an off-site target, oldest first, on every node — for example those made before a target was set up.

{% if active_targets == 0 && targets_error.is_none() %}

no target in use There is nowhere to copy to yet — see Off-site targets.

{% endif %}
What the two buttons do
  • Off-site copies are made as each backup runs, so anything already on local disk when a target was set up was never sent. The copy walks the backups with no off-site copy recorded — oldest first, because the oldest is closest to being pruned off local disk — and uploads them.
  • It runs as a background job on {% if chrome.has_nodes %}the master and every node at once, each over the backups of the sites it owns; the job log reports each node{% else %}this server{% endif %}. One run copies at most 200 backups per node: run it again to continue.
  • Backups whose archive was already pruned are reported separately and counted as gone: nothing can retry those.
  • Copy off-site & delete local also deletes each local copy once it has been independently re-verified off-site — including copies that were already off-site, which are re-checked where they are rather than uploaded again. Each site's newest copies set under Local copies stay. A copy that cannot be confirmed (missing, wrong size, or the target unreachable) is kept, so this never deletes the only copy.
